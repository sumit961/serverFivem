# cm-crafting: shared crafting framework (v1.0)

`cm-crafting` orchestrates **item input -> item output** crafting sessions for any content resource: recipe and station registry, a server-timed
session, final revalidation, and a single idempotent settlement through the inventory owner. It is a framework, not a catalogue: it ships **no real
recipes, items, materials or stations**.

```
CLIENT -> content resource SERVER (physical interaction, animation, minigame, progression) -> cm-crafting exports -> cm-inventory (settlement)
```

There is **no client event, NUI callback, command or manifest client script**. It handles no money and defines no prices.

## Required cm-inventory contract (the smallest safe primitive)

Trusted caller only (`GetInvokingResource() == 'cm-crafting'`), addressed by **character id** (works offline), idempotent by `reference`:

```lua
-- tx is generated by cm-crafting from the registered recipe; the client never supplies any part of it
tx = { inputs  = { { item = 'test_log',  amount = 4 } },
       outputs = { { item = 'test_plank', amount = 2, metadata = { quality = 'basic' } } },   -- static recipe metadata only
       tools   = { { item = 'test_saw', durabilityUse = 2 } } }                                -- required, not consumed; durabilityUse optional

ValidateCraftTransaction(characterId, tx)        -> true | false, 'insufficient_input' | 'tool_missing' | 'no_capacity' | 'invalid_transaction'   (read only)
ExecuteCraftTransaction(reference, characterId, tx)
        -> true, { replayed = bool }             -- committed (or already committed under this reference)
        |  false, 'insufficient_input' | 'tool_missing' | 'no_capacity' | 'invalid_transaction'   -- DEFINITE failure: NOTHING was applied
        |  false, 'unavailable'                  -- unknown outcome: caller must reconcile via status
GetCraftTransactionStatus(reference)             -> 'committed' | 'not_applied'             -- authoritative ledger lookup, safe to call any time
```

`ExecuteCraftTransaction` must, in **one SQL transaction**: verify every input and tool, verify output capacity (slots/stack/weight/metadata rules via cm-items),
consume inputs, apply tool durability, create outputs, and insert the `reference` into a UNIQUE ledger. A repeated `reference` returns committed without applying anything again.
cm-crafting detects the contract by probing `GetCraftTransactionStatus`; the console command `cm_crafting_status` and export `IsCraftingSettlementReady` report it.
This primitive is **one-party** (A's inputs -> A's outputs). It is not the two-party exchange `cm-trade` needs and must not be advertised as solving it.

## Recipe registry

`Config.TrustedOwners` (resource names, checked with `GetInvokingResource()`) ships **empty = fail closed**. A recipe is pinned to its registering resource; the same owner may
re-register (restart / hot reload), another resource using the same id gets `owner_mismatch`. **Recipes are not persisted**: content owners re-register on start and on the local
server event `cm-crafting:server:registryReady` (not networked), so a late-starting owner needs no server restart.

Recipe id: `<namespace>:<name>` (`^[a-z0-9_]+:[a-z0-9_]+$`, e.g. `mining:iron_ingot`). Registration rejects: malformed ids/labels, empty or oversized line lists, duplicate item lines, non-integer / zero / negative /
over-limit amounts (including `amount x maxBatch` overflow), recursive recipes (an output that is also an input/tool), invalid duration (per unit 1-3600 s, total <= 7200 s), bad batch limits (<= 50),
neither `handcraft` nor `stations` (never "craftable anywhere" by omission), any function value (no callback code), non-plain output metadata, and **any item cm-items does not know** (cm-items unavailable = `items_unavailable`, fail closed).

```lua
{ id = 'test:plank', label = 'Plank', category = 'sawmill', durationSeconds = 10,   -- per unit
  batch = { min = 1, max = 5 }, stations = { 'sawmill' }, handcraft = false,
  inputs = { { item = 'test_log', amount = 2 } }, outputs = { { item = 'test_plank', amount = 1, metadata = { quality = 'basic' } } },
  tools = { { item = 'test_saw', durabilityUse = 1 } },
  eligibilityExport = 'CanCraftHere' }   -- optional: export on the OWNER resource: (characterId, recipeId, quantity, stationId) -> true | false, reason
```

## Stations

`RegisterCraftStation({ id, type, coords = {x,y,z}, radius = 0.5..25, bucket = nil|int, shared = false })`: owner-pinned, server-known coordinates only. A recipe lists the station **types** it accepts; the station must be owned by the recipe's owner
(or be `shared`). Client coordinates are never an authority: the server reads the character's position, requires the station's routing bucket (if set) and distance <= radius at **begin and again at completion**.
`handcraft = true` recipes need no station; a recipe that is not handcraft refuses to start without one. Physical locations, props and animations belong to content resources.

## Craft session

States: `active` -> `committing` -> `completed`; terminal alternatives `cancelled`, `failed`, `expired`.

1. **Begin** (`BeginCraft(characterId, recipeId, quantity, stationId, ctx)`): trusted owner of the recipe; character id format + online; integer quantity within the recipe batch; station + bucket + range; owner eligibility export
   (failure = deny); settlement contract ready; `ValidateCraftTransaction` (inputs/tools/capacity *appear* available); one live craft per character (UNIQUE `active_key`); rate limit. The server builds the **transaction snapshot** from the
   registered recipe (inputs/outputs scaled by quantity) and stores it; `ctx` only accepts `idempotencyKey` and a trusted `speedModifier`, everything else is ignored.
   Duration = `durationSeconds x quantity / modifier` (modifier clamped 0.5-2.0), never below 1 s. **No input is consumed at start** (no reservations): if the player uses the ingredients elsewhere, the final commit fails safely.
2. **Timer**: `ready_at` is server time. Early `CompleteCraft` returns `too_early`. A session expires `600 s` after it was ready.
3. **Complete** (`CompleteCraft(ref, characterId, ctx)`): ownership + character pin; timer reached; owner recipe still registered; character online; same bucket; still at the station; eligibility again; `ValidateCraftTransaction` again
   (missing input/tool/capacity -> the session **fails**, nothing consumed). One compare-and-swap `active -> committing` decides any complete/cancel/expiry race, journals `commit_started`, then `ExecuteCraftTransaction(reference, ...)`.
   `completed` is written **only after** the inventory reports committed (journals `inventory_committed`, `completed`). A definite inventory refusal fails the session; an unavailable/unknown outcome keeps it `committing` for reconciliation.
   The result is the authoritative outputs list; repeats return the same result (`replayed`).
4. **Cancel** (`CancelCraft`): only while `active`; nothing was consumed, so no refund exists. `committing`/`completed` -> `cancel_not_allowed`. **Fail** (`FailCraft`) is for content interruptions (death, custody, movement); not allowed while committing.
5. **Disconnect**: an offline crafter fails the session after 60 s (no offline outputs, nothing lost). A `committing` session is reconciled regardless of presence.
6. **Recovery** (at start and every 5 s): `active` sessions fail on restart (`restart`; a pre-restart timer is not trusted); `committing` sessions ask `GetCraftTransactionStatus`: committed -> `completed` (no re-apply); `not_applied` -> the idempotent
   execute is retried (<= 5 attempts then `commit_failed`); unknown -> stays `committing` and is flagged (`reconcile_stuck`, admin audit) after 15 min. The core never guesses and never re-applies without the inventory's ledger.

## Database (additive, idempotent)

`cm_crafting_sessions`: `reference` UNIQUE (= the inventory transaction reference), `active_key` UNIQUE (character id while `active`/`committing`), `idem_key` UNIQUE (`<owner>:<key>`), status, recipe, owner, character, station, quantity, bucket, `started_at`/`ready_at`/`expires_at`/`committed_at`, `tx_json` snapshot, `commit_attempts`, `failure_reason`; indexes `(status, expires_at)`, `(character_id, id)`.
`cm_crafting_events` (append-only): `journal_key` UNIQUE for once-only `started`, `commit_started`, `inventory_committed`, terminal, `reconcile_stuck`. Kinds: `started`, `commit_started`, `inventory_committed`, `completed`, `cancelled`, `failed`, `expired`, `reconciled`, `admin_cancel`, `reconcile_stuck`.
No source id, account identifier or arbitrary metadata is stored. Recipes/stations are runtime-registered, not persisted.

## Consumer guide (Agent 3 / Agent 4)

```lua
-- 1. register (start + registryReady). Add the resource name to cm-crafting Config.TrustedOwners first.
local function register()
    exports['cm-crafting']:RegisterCraftRecipe({
        id = 'lumber:plank', label = 'Plank', category = 'sawmill', durationSeconds = 12, batch = { min = 1, max = 10 }, stations = { 'sawmill' },
        inputs = { { item = 'log', amount = 2 } }, outputs = { { item = 'plank', amount = 1 } },     -- items must exist in cm-items (and be an approved material catalog entry)
    })
    exports['cm-crafting']:RegisterCraftStation({ id = 'sawmill_1', type = 'sawmill', coords = vec3(-550.0, 5300.0, 74.0), radius = 3.0 })   -- 2. station
end
AddEventHandler('onResourceStart', function(r) if r == GetCurrentResourceName() then register() end end)
AddEventHandler('cm-crafting:server:registryReady', register)

-- 3. player pressed E at the station (your client -> YOUR server). Resolve the character yourself; never take it from the client
RegisterNetEvent('lumber:server:startPlank', function(quantity)
    local cid = tostring(exports['cm-playerdata']:GetCharacterId(source))
    local ok, s = exports['cm-crafting']:BeginCraft(cid, 'lumber:plank', math.floor(tonumber(quantity) or 1), 'sawmill_1', { idempotencyKey = ('plank:%s:%d'):format(cid, os.time() // 10) })
    if not ok then return notify(source, s) end               -- settlement_unavailable / insufficient_input / too_far / ...
    crafts[cid] = s.reference
    TriggerClientEvent('lumber:client:progress', source, s.durationSeconds)   -- 4. your animation / minigame (cosmetic; the SERVER timer decides)
end)
-- 5. when your gameplay says it finished (death/movement -> exports['cm-crafting']:FailCraft(ref, 'interrupted'))
RegisterNetEvent('lumber:server:finishPlank', function()
    local cid = tostring(exports['cm-playerdata']:GetCharacterId(source))
    local ok, result = exports['cm-crafting']:CompleteCraft(crafts[cid], cid, {})
    if ok then notify(source, ('Crafted %dx %s'):format(result.outputs[1].amount, result.outputs[1].item))   -- 6. authoritative result; settlement already happened
    elseif result == 'too_early' or result == 'too_far' then notify(source, result) end                      -- retryable; anything else ended the craft
end)
```

## Boundaries and future integration

* **Mining / lumber / recycling** own gathering, tools, progression and nodes; cm-crafting owns the refining recipe + settlement. Gathering outputs stay disabled until the material catalog is approved.
  This task assigns **no value to any item**, enables **no material reward**, and does not re-enable the disabled recycling material rewards.
* **Construction / warehouse** consume approved crafted materials; cm-crafting owns neither projects nor warehouse stock.
* **Mechanic parts** (future): materials -> crafting -> parts -> business supply/storage -> mechanic service. `cm-mechanic` is unchanged.
* **Crime** (future): an organization/crime owner registers its specialized recipes and station and validates eligibility through `eligibilityExport`. `cm-crime` does not own crafting; cm-crafting does not own crime sessions.
* **cm-contracts**: not used for crafting. A future production contract wraps *production gameplay* which calls cm-crafting.
* **Business manufacturing** (future): needs a business-owned inventory/storage contract (character inventory is the wrong custody), plus employee permissions via `cm-commercial-ownership`. Not implemented; the transaction contract above is character-scoped on purpose until that owner exists.
* **Tools / durability**: tools are required-not-consumed catalysts; `durabilityUse` is passed through to the inventory contract (bounded 1-100 x quantity). cm-crafting never mutates durability itself: **PARTIAL** (contract defined, settlement owner pending).
* **No money**: no fees, licences or machine costs exist here; they belong to the owning business/system.
* **cm-trade** is not addressed: its blocker (atomic two-party exchange) is separate.
